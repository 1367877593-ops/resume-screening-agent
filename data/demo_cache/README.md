# Demo cache

这里的 JSON 文件是仓库内置样例的结构化响应回放。`make demo` 使用固定的
`demo / demo-v1` 缓存命名空间，因此不受评审者本机 `.env` 中 provider、模型名
或 API Key 的影响，也不会发起网络请求。

这些响应由 `scripts/generate_demo_cache.py` 中经过人工核对的夹具生成：每条引用
都能在 `data/samples/` 的原文中找到，完整结果会再次经过同一套 Pydantic Schema、
Checker、代码算分和排序状态机，而不是绕过业务逻辑直接展示静态页面。

当前 25 条，对应一次完整运行的全部模型调用：

| 阶段 | 条数 |
|---|---|
| JD 拆解 | 1 |
| 简历提取 + 匹配判定（三位候选人） | 6 |
| 语义一致性校验（三位候选人各一次） | 3 |
| 李明：出题（首轮 9 道）+ 修订补齐 | 2 |
| 李明：三人格作答 + 盲评阅卷 | 4 |
| 李明：追问生成 | 1 |
| 陈涛：出题 | 1 |
| 陈涛：三人格作答 + 盲评阅卷 | 4 |
| 陈涛：追问生成 | 1 |
| **第二轮**两位候选人的出题（注入飞轮经验后 prompt 变了） | 2 |

王芳被一票否决，因此不出题、不盲评 —— 这本身也是被演示的业务规则之一。

内置样例刻意保留四处不完美：

1. 首轮题目数量不足，被确定性规则打回一轮（`rule`）
2. 李明那道通用故障排查题被盲评判为「无区分度」（`sim`）
3. 陈涛那道向量检索题被判「超出射程」（`sim`）
4. 陈涛 R5 的理由与其所引原文自相矛盾，被语义校验抓出（`llm`）

连跑两次还能看到反思飞轮：第一轮题数不足被打回一轮，第二轮带着经验一次给足 10 道、
零轮修订。第三轮起经验集合不再变化（只有命中次数在涨，而它不进 prompt），
因此继续命中缓存。

三种 detector 因此各触发至少一次 —— 任何一档长期为 0，「规则 vs LLM 检出占比」
这个数字就说明不了任何问题。Demo 展示的是这些机制在工作，而不是一份摆拍的完美结果。

修改样例、Prompt 版本或 Schema 后重新生成并验证：

```bash
make demo-cache
```
